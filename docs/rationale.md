# Rationale: why each component is built the way it is

For a reviewer who asks "why did you do it this way?". Every component below has the same five parts: **Problem** (the threat or requirement, with threat IDs from [threat-model.md](threat-model.md)), **Decision** (what is built, with links), **Alternatives rejected**, **Trade-offs and limits** (honest, with accepted-risk IDs from [accepted-risks.md](accepted-risks.md)), and **Proof** (the test, attack ID or CI check that shows it works). Anything that is not backed by a test, a file or a decision record is marked **unverified**.

The system is a lab with a deliberately plain product (case files with attachments, classification, units, compartments). The product is a vehicle; the access-control design and the evidence are the subject. Decision records are in [decisions.md](decisions.md) (ADR-n).

## 1. Monorepo and pnpm

- **Problem.** The same rules are implemented in four places (policy package, API guard, SQL, tests) and must not drift. Supply-chain risk starts at install time (T-32).
- **Decision.** One pnpm workspace ([pnpm-workspace.yaml](../pnpm-workspace.yaml)): `apps/api`, `apps/web`, `packages/{policy,audit,netguard}`, `tests/*`. TypeScript strict, ESM (ADR-5). The policy package is the single source of the vocabulary and the rules; the API, the BFF display, the SQL parity tests and the attack tests import or mirror it. Installs run with `ignore-scripts=true`, a frozen lockfile and a 24 hour minimum release age ([.npmrc](../.npmrc), [supply-chain.md](supply-chain.md)).
- **Alternatives rejected.** Separate repositories (the policy package could drift from the SQL it must match, and a cross-repo change cannot be one reviewed commit); npm or yarn (pnpm's strict `node_modules` layout makes an undeclared dependency a build error, and its release-age setting is the control used here).
- **Trade-offs and limits.** One CI run builds everything; the monorepo makes the shared packages' build order matter (`pnpm typecheck` builds the two compiled packages first). The release-age floor is low (24 hours) because the lockfile was resolved with recent releases ([supply-chain.md](supply-chain.md)).
- **Proof.** `pnpm lint` and CI `check` ([ci.yml](../.github/workflows/ci.yml)); the install-scripts-off claim is checked by CI building and testing without them.

## 2. Keycloak as the identity provider

- **Problem.** Authentication is the part most often built wrongly. Credential storage, MFA, brute-force defence, token issuing and key rotation are products, not features (T-02, T-18 to T-23).
- **Decision.** Keycloak 26 ([ADR-2](decisions.md)). The realm is code ([realm-casefile.json](../infra/keycloak/realm-casefile.json), T-20): a confidential client for the web app with PKCE, a separate audience for the API, access tokens of five minutes, refresh-token rotation with reuse detection, brute-force detection, no self-service profile edits of clearance, unit or compartments (T-19). The authorization attributes travel as claims (`clearance`, `unit`, `compartments`, realm roles) through protocol mappers (ADR-6). TOTP is required for the SECRET users, and the strength of the sign-in is carried as `acr` (`pwd` = 1, `mfa` = 2) and `amr`; a request that needs more than the session has gets an RFC 9470 step-up challenge, and the BFF restarts the login with `acr_values=mfa` ([identity.md](identity.md)).
- **Alternatives rejected.** Hand-written login with a password table (every item above would be ours to get right and to test); a managed identity service (not reproducible in CI and not inspectable); putting authorization data only in a database lookup (claims make the API's decision verifiable from the token alone; ADR-6 states what stays out of the token).
- **Trade-offs and limits.** Claims are as old as the token (at most five minutes), so a changed clearance takes effect at the next refresh or login; the lockout feature can be used to lock a user out (AR-13); account recovery, user notification, a breached-password check and MFA for the Keycloak admin console are not configured (AR-14); step-up has no freshness window beyond the session's own `acr` (AR-03). The dev compose runs `start-dev` over HTTP on loopback; the prod-like stack runs the production-mode image behind TLS ([deployment.md](deployment.md)). Several password-policy rows are **delegated** and unverified in [asvs.md](asvs.md).
- **Proof.** [tests/identity](../tests/identity): real logins through the HTML forms, PKCE negatives (none, `plain`, wrong redirect, code reuse, wrong verifier), claims, refresh rotation and reuse, lockout, MFA. Attacks A-09, A-10, A-16, A-73, A-83 ([attack-catalogue.md](attack-catalogue.md)).

## 3. The BFF (backend for frontend)

**What it is.** A server-side component that the browser talks to. It performs the OAuth flow, holds the tokens and calls the API on the user's behalf. Here it is the Next.js app in [apps/web](../apps/web): server-rendered pages, route handlers for forms and a narrow JSON proxy, and a Postgres session store.

**The problem with the alternative.** In a single-page app that holds the tokens itself, access and refresh tokens must live somewhere script can reach: memory, `localStorage`, `sessionStorage`, or a cookie that script can read. Any cross-site scripting bug or malicious dependency then reads them and uses them from anywhere, at once; the tokens are bearer credentials, so theft takes one step and leaves no trace on the victim's device. Refresh-token handling in a browser (rotation, concurrent refresh, reuse detection) is hard to make safe, and CORS plus short lifetimes become the only defences left. For a system whose whole point is that a clearance-limited user must not be able to hand their access to someone else, that is the wrong place for the credentials.

**What the BFF changes.**

- The browser holds one opaque cookie: `__Host-casefile_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, path `/`, no `Domain`. Its value is 32 random bytes; the database stores only its SHA-256 ([session-store.ts](../apps/web/src/server/session-store.ts), T-40). The `__Host-` prefix pins the cookie to the exact host and forbids overwrites from sibling subdomains.
- Tokens live server-side, AES-256-GCM encrypted with a key ring and the row's key hash as additional data. Refresh and rotation run under a row lock, a refused refresh destroys the session, and a replayed refresh token ends it (T-21, T-39).
- Logout is a POST that destroys all of the user's sessions and calls Keycloak's end-session with `id_token_hint` (T-06).
- The API can stay a pure bearer-token resource server that trusts nothing but a validated JWT ([section 4](#4-the-api-as-a-resource-server)): it never sees a cookie.
- The BFF is the one place for CSRF defence (synchronizer token plus Origin and `Sec-Fetch-Site`, ADR-15), security headers and the CSP with a per-request nonce, rate limits, the signed network zone ([section 10](#10-rate-limiting-the-signed-network-zone-and-the-trusted-proxy-contract)) and the allow-listed API client: a fixed set of method and path pairs against a fixed host, upstream requests built from scratch, so it is not an open proxy or an SSRF gadget (ADR-16, T-38).

**The costs, stated honestly.**

- One more component to run and secure, with its own database role (`casefile_web`, which sees only the session table, ADR-14).
- Cookie sessions need CSRF defence. This is where a real defect was found: with `Referrer-Policy: no-referrer`, Chromium sends `Origin: null` on same-origin form posts, so the (correct) CSRF check refused every real form post. All earlier tests set `Origin` by hand; only the real-browser test caught it. The web app now sends `same-origin` ([ADR-25](decisions.md)).
- A server-side store and key management: the session key ring, the audit key ring and the database passwords need rotation procedures ([hardening.md](hardening.md) section 3; no key management service, no tested live rotation, **unverified** beyond the unit tests).
- A compromised BFF can use live sessions and claim any network zone for its users (AR-05); it holds the tokens by design.
- Stateful sessions complicate horizontal scaling: the store is shared (Postgres), but the rate-limit counters are per process (AR-04) and nothing here was run with more than one replica (**unverified**).

**Why it is the right fit here.** The data model is classified: a stolen token must not be possible from the browser, and the policy depends on `acr`, so the server must control the login and step-up flow anyway. The IETF draft "OAuth 2.0 for Browser-Based Apps" names the BFF pattern as the most secure architecture for browser-based applications; the wording and the draft's current status are **to be verified against the current text before publishing**.

## 4. The API as a resource server

- **Problem.** Whatever reaches the API must be proven to come from the identity provider, for this API, for this client, and must fail closed when anything is missing or odd (T-08 to T-10, T-33).
- **Decision.** [token-verifier.ts](../apps/api/src/auth/token-verifier.ts) uses `jose` ([ADR-8](decisions.md)): an asymmetric algorithm allow-list (`none` and every HS* rejected by omission), signature against the realm's JWKS with a cache that refetches on an unknown `kid` at most once per cooldown, `iss`, `aud`, `azp`, `exp`, `nbf` with a small clock skew. The principal is parsed fail closed: a missing or malformed claim is an error, never a default; unknown roles carry no grants. The token is validated offline, per request; the API trusts no cookie and no header other than the Bearer token and the BFF's signed zone header.
- **Alternatives rejected.** Introspecting every token at Keycloak (a network call per request and a new availability dependency; offline validation is the standard resource-server model); hand-rolled JWT parsing (the allow-list and the failure cases are exactly what a library has already been attacked for); a permissive principal with defaults (a default is a privilege).
- **Trade-offs and limits.** Offline validation cannot see a logout: an access token works for its remaining life, at most five minutes (AR-02; measured in A-08, the refresh token is dead at once). A retired signing key verifies until the JWKS cache refreshes. TLS between the BFF and the API is not built (AR-01).
- **Proof.** [token.test.ts](../apps/api/src/token.test.ts) (tampered payload, `alg=none`, HS256 with the public key as the secret, unknown or reused `kid`), [rotation.test.ts](../apps/api/src/rotation.test.ts), [routes.test.ts](../apps/api/src/routes.test.ts) (every route is guarded), [api-auth.test.ts](../tests/identity/src/api-auth.test.ts) with real tokens; attacks A-01 to A-06, A-72, A-91 ([jwt-api.test.ts](../tests/attack/src/jwt-api.test.ts)). Details: [api-auth.md](api-auth.md).

## 5. RBAC plus ABAC and the policy package

- **Problem.** "May this person do this to this record" depends on role, the person's clearance, unit and compartments, the record's classification, unit, compartments and status, and the situation (authentication strength, time, network zone). The rule must be testable, not scattered (T-11, T-12, T-13, T-16, T-17, T-25).
- **Decision.** RBAC answers the coarse question (does the role grant the action at all), ABAC the per-record one ([ADR-3](decisions.md)). Both live in one package of pure functions, [packages/policy](../packages/policy): default deny, deny overrides allow, a reason code and the matching rules with every decision. Separation of duties: nobody approves what they wrote. Break-glass is a narrow, audited exception for one role: it needs a justification, never lifts the SECRET floor, and raises an alert ([policy.md](policy.md)). A file the caller may not read answers 404, the same as a missing file, so the API never tells hidden from forbidden ([ADR-9](decisions.md)); the real reason goes only to the audit log ([section 8](#8-the-hash-chained-audit-log)). UI hiding is cosmetic: every decision is server-side.
- **Alternatives rejected.** RBAC only (role explosion, cannot express need-to-know); an external policy engine (a second language and runtime for a rule set this small, and the same engine would not run inside Postgres); checks inside controllers (T-11: one forgotten check is a leak); 403 for hidden files (it confirms existence).
- **Trade-offs and limits.** The 404 rule costs debuggability (the client cannot be told why); step-up has no freshness window (AR-03); break-glass has no second approver and no alert consumer (AR-09). Rules exist in three copies on purpose (policy package, SQL, the attack tests' expectations); [section 6](#6-postgres-row-level-security-and-the-parity-tests) explains how drift is caught.
- **Proof.** [packages/policy](../packages/policy) tests with a coverage gate, the full role by action matrix; [policy.test.ts](../apps/api/src/policy.test.ts) (existence hiding, step-up challenge, ownership, lifecycle, export zone and window, break-glass); route inventory ([routes.test.ts](../apps/api/src/routes.test.ts), T-11); attacks A-20 to A-26, A-60, A-61, A-82 ([authz.test.ts](../tests/attack/src/authz.test.ts), [breakglass-stepup.test.ts](../tests/attack/src/breakglass-stepup.test.ts)).

## 6. Postgres row-level security and the parity tests

- **Problem.** An application-level check can be forgotten or bypassed (an injection, a new endpoint, a bug). If the database trusts the application completely, a single missed check is a leak (T-14, T-15, T-36, T-37).
- **Decision.** Row-level security, forced, on the case-file tables ([data-layer.md](data-layer.md), ADR-4, ADR-11): the API connects as a non-owner role without `BYPASSRLS`, sets the request context (`is_local => true`, inside the request's own transaction, never per session) and the policies re-implement the read and write rules in SQL. A guard trigger and column grants limit what an update may change; separate migrator and app roles; a startup check refuses an unsafe role. Plain SQL with `pg` and no ORM (ADR-10): SQL is built only from `$n` parameters, and a lint rule rejects template-literal SQL.
- **Alternatives rejected.** Application checks only; an ORM with a tenant filter (a filter is another application check); a view-per-clearance layer (does not express compartments and status).
- **Trade-offs and limits.** The rules exist in two implementations, which is the point and the cost: they can drift. The defence is the parity suite, which runs the same cases through the policy package and through SQL and requires equal answers. The denial reason for an audit row needs a narrow `SECURITY DEFINER` function, a one-bit existence oracle for a compromised API role (ADR-19, AR-12).
- **Proof.** [tests/api-db](../tests/api-db) against real Postgres: parity, superuser and owner probes, forced RLS, role checks (T-15, T-36, T-37); injection attacks A-30; the attachment table's policies follow the parent's ([section 9](#9-attachments)). Hand mutants of the SQL and the app layer are recorded in [data-layer.md](data-layer.md) and [hardening.md](hardening.md).

## 7. Transactions and check-then-use races

- **Problem.** If the decision is made on one state and the write happens on another, an edit lands on a submitted file, an approval is doubled, or an author wins a race (T-35).
- **Decision.** Load with a row lock, decide on the locked row, write, all in one transaction ([ADR-12](decisions.md), [case-file.service.ts](../apps/api/src/casefiles/case-file.service.ts)): the application decision is authoritative and the database checks the same rules again. A lock timeout, serialization failure or deadlock is a retryable 409.
- **Alternatives rejected.** Optimistic version checks only (they do not protect the decision itself, only the write); advisory locks per record (a second locking scheme to keep correct).
- **Trade-offs and limits.** Row locks serialize writers of one file; throughput under contention is **unmeasured**.
- **Proof.** [tests/api-db](../tests/api-db) concurrency cases; attack A-23 (status machine, self-approval) and A-46 (races around uploads).

## 8. The hash-chained audit log

- **Problem.** Decisions, break-glass reads, sign-ins and auditor reads must be recorded, and the record must show if it was altered, deleted or cut (T-24, T-25, T-26, T-41, T-42).
- **Decision.** [packages/audit](../packages/audit) and [audit.md](audit.md): every row carries `prev_hash` and an HMAC-SHA256 over its canonical form with a key from a ring; ids are gap-free; a head table, an advisory lock and a database trigger make the chain linear; no `UPDATE`, `DELETE` or `TRUNCATE` is granted and triggers raise for every role (a superuser or the owner can still disable the triggers; the break procedure is documented in [audit.md](audit.md) and is not available to any application role). Checkpoints are MACs of the head. An audit row is written before the action and the action fails if the row cannot be written (fail closed for allows; best effort for refusals and sign-out, ADR-18). Free text is limited to a sanitised break-glass justification; a fixed `details` schema and a CSV exporter that defuses formulas (T-42). An auditor-only API and page read, verify and export; every export is itself audited and carries a proof of the head it was produced against.
- **Alternatives rejected.** A plain log table (no tamper evidence); a blockchain or a transparency-log product (a service and a trust root for no gain at this size); logging to files only (not queryable by the auditor role, not protected by grants).
- **Trade-offs and limits.** The chain proves that rows were not changed, reordered or removed **without the key**; it does not prove the writer told the truth, and anyone holding the HMAC key can forge a consistent chain. Checkpoints are not anchored outside the database (AR-08), so a database administrator with the key could rewrite history consistently; there is no WORM copy. Retention, partitioning and write throughput are unmeasured at scale.
- **Proof.** [audit.test.ts](../packages/audit/src/audit.test.ts) (chain, tamper, cursors), [audit-db.test.ts](../tests/api-db/src/audit-db.test.ts), [audit-api.test.ts](../tests/api-db/src/audit-api.test.ts) (every decision audited with the real reason; fail closed when the table is unwritable), [audit-bff.test.ts](../tests/bff/src/audit-bff.test.ts); attacks A-50 to A-53 ([audit-tamper.test.ts](../tests/attack/src/audit-tamper.test.ts)) with a stolen database credential; the mutation tallies in [audit.md](audit.md).

## 9. Attachments

- **Problem.** An uploaded file is untrusted bytes with an attacker-chosen name; a download is the easiest way to run active content in the application's origin; a file can be swapped after review (T-28 to T-31, T-47).
- **Decision.** [ADR-21](decisions.md), [hardening.md](hardening.md) section 4: the bytes decide the type against a four-type allow-list (PDF, PNG, JPEG, plain text) and the declared type must agree; archives are refused; names are cleaned and never used as paths; files are stored under random 128-bit keys in a dedicated directory outside any web root; SHA-256 and size are stored and checked on every read; a file stays in `quarantine` until the scanner gives an explicit clean verdict (ClamAV over INSTREAM), a scanner error or timeout leaves it `pending`; only `clean` is downloadable, as an attachment with `nosniff`, a type from a fixed list and a `sandbox` CSP; downloads go through the API only; the attachment table's row-level security asks the parent case file's own policy, so there is no copy of the rule to drift.
- **Alternatives rejected.** Trusting the extension or the declared type; sniffing a few bytes (polyglots); an object store with presigned URLs (bearer URLs outlive a revoked session and bypass the policy); serving inline after sanitising (a sanitiser is a second product to trust).
- **Trade-offs and limits.** No storage quota (AR-06); pending files are never re-scanned (AR-11); the PDF check is a marker scan and not a sanitiser, and detection by ClamAV is demonstrated only for EICAR (AR-10); attachments cannot be removed; a draft with attachments cannot be deleted.
- **Proof.** [content.test.ts](../apps/api/src/attachments/content.test.ts), [attachments-api.test.ts](../tests/api-db/src/attachments-api.test.ts), [attachments-bff.test.ts](../tests/bff/src/attachments-bff.test.ts); the prod-like test uploads EICAR through a real login and requires quarantine; attacks A-40 to A-46, A-92 ([uploads.test.ts](../tests/attack/src/uploads.test.ts)); 43 hand mutants recorded in [hardening.md](hardening.md).

## 10. Rate limiting, the signed network zone and the trusted-proxy contract

- **Problem.** Brute force and exhaustion (T-22, T-27, T-45), and a rule that depends on where the request comes from (export only from the managed network) when the API can see only the BFF's address (T-44).
- **Decision.** [packages/netguard](../packages/netguard) ([hardening.md](hardening.md), ADR-20): a bounded fixed-window limiter; per-user and per-address limits at the BFF and per-subject limits at the API. A forwarded header is believed only when the request carries the reverse proxy's shared secret (the proxy overwrites it and strips every inbound `x-acl-*` and forwarded header); otherwise all clients are one address. The BFF decides the zone from the proxy-vouched client address and sends it as an HMAC-signed, per-subject, short-lived header (`x-acl-zone`, key ring, 30 second freshness); the API honours a zone only if it verifies for the token's subject. Canonical encoding: the MAC has exactly one valid spelling.
- **Alternatives rejected.** Trusting `X-Forwarded-For` (a client chooses its own address); trusting the socket address behind a proxy (everyone is the proxy); sending the zone as a plain header (anyone calling the API claims it); an API gateway product (a component for four rules).
- **Trade-offs and limits.** Counters are per process and one address is one bucket (AR-04); a compromised BFF can claim any zone for its users (AR-05); nothing here was run with more than one replica (**unverified**). The zone MAC check was found weak by a flaky test: the last character of the 43-character base64url MAC carries only 4 bits, so four of the 64 characters decode to the same bytes, and the verifier accepted all four; it now refuses non-canonical spellings, and the forged-MAC test flips a decoded byte ([hardening.md](hardening.md), "Found later by a flaky test").
- **Proof.** [netguard.test.ts](../packages/netguard/src/netguard.test.ts) (including the single-spelling test, which fails if the check is removed), [hardening-bff.test.ts](../tests/bff/src/hardening-bff.test.ts), [policy.test.ts](../apps/api/src/policy.test.ts) (zone claims from anyone but the BFF are ignored); prod-like test (forged client addresses through the real proxy share the real bucket); attacks A-07, A-26, A-70 to A-76 ([ratelimit-proxy.test.ts](../tests/attack/src/ratelimit-proxy.test.ts)); 25 hand mutants in [hardening.md](hardening.md).

## 11. The production profile

- **Problem.** Development values (default passwords, short keys, plain HTTP, insecure cookies, a stub scanner) must not reach production, and an operator who forgets a switch must not get the lenient behaviour (T-46, T-18).
- **Decision.** `ACL_ENV=production` (not `NODE_ENV`, which `next start` sets for every deployment, including tests) makes the API and the BFF refuse, at startup, development markers, short or low-entropy keys, plain HTTP, insecure cookies and the stub scanner. A typo in the profile name is an error. Secrets can come from files (`NAME_FILE`); giving both forms is an error. The application images set `ACL_ENV=production` themselves ([ADR-22](decisions.md)).
- **Alternatives rejected.** Documenting the shape only; `NODE_ENV` as the switch; one lenient default with warnings.
- **Trade-offs and limits.** Entropy checks are heuristics; a strong-looking weak secret passes. Error messages never carry a secret value (tested with a canary), which makes some failures terse.
- **Proof.** The "production profile" tests in [config.test.ts](../apps/web/src/server/config.test.ts) and [config.test.ts](../apps/api/src/config.test.ts); the prod-like test starts the images with development values and requires a refusal ([deployment.md](deployment.md)).

## 12. Containers and the prod-like stack

- **Problem.** Hardening that is only described is not hardening, and an image is a supply-chain and a runtime risk (T-32, T-34, T-27).
- **Decision.** [Dockerfile.api](../Dockerfile.api), [Dockerfile.web](../Dockerfile.web), [Dockerfile.keycloak](../Dockerfile.keycloak), [Dockerfile.caddy](../Dockerfile.caddy), [Dockerfile.clamd](../Dockerfile.clamd): multi-stage, base images pinned by digest, application images distroless and non-root; the prod-like compose ([docker-compose.prod-like.yml](../docker-compose.prod-like.yml)) runs every container read-only with all capabilities dropped and `no-new-privileges`, secrets as files, four networks of which three are internal (only the proxy is routable), and a [Caddy](../infra/caddy/Caddyfile) proxy that terminates TLS and overwrites the proxy secret and client address. The stack is attacked from outside by [scripts/prod-like-test.mjs](../scripts/prod-like-test.mjs) ([ADR-22](decisions.md)). The proxy and scanner images are built here because the stock ones had fixable HIGH findings ([ADR-23](decisions.md)).
- **Alternatives rejected.** Kubernetes manifests (more machinery than the claim needs and nothing here to run them); stock Caddy and ClamAV images with an ignore list (26 exceptions would train people to ignore the list).
- **Trade-offs and limits.** No TLS between internal components (AR-01); we own the rebuild schedule of the images we build and the scanner signatures are as old as the image (AR-15); a certificate from a public CA, HTTP/3, a cloud load balancer, backups, log shipping and host hardening are **not verified** ([deployment.md](deployment.md)).
- **Proof.** CI `prod-like` and `images` (Trivy on every built image, SBOM per image); the prod-like test with 22 hand mutants of the compose file, Caddyfile and Dockerfiles, all killed except one inert mutant ([hardening.md](hardening.md)).

## 13. Supply chain

- **Problem.** A dependency, an action or an image can be malicious or vulnerable, and a secret can be committed (T-01, T-32).
- **Decision.** [supply-chain.md](supply-chain.md): frozen lockfile, install scripts off, a minimum release age, Dependabot with a cooldown and auto-merge only for minor and patch updates behind required checks, every action pinned by commit SHA, image digests, CodeQL (security-extended, uploaded to code scanning), OSV-Scanner, Trivy with a dated and reasoned exception file ([check-trivyignore.mjs](../scripts/check-trivyignore.mjs)), CycloneDX SBOMs, gitleaks over the full history, actionlint and zizmor for the workflows, OpenSSF Scorecard, and an invisible-character guard ([check-invisible-chars.mjs](../scripts/check-invisible-chars.mjs): bidirectional and zero-width characters in source are rejected, which is how a "Trojan Source" change would arrive).
- **Alternatives rejected.** Version ranges and trust in the registry; ignoring scanner findings without an expiry.
- **Trade-offs and limits.** Dependencies and base images are trusted at build time (AR-15); the release-age floor is low; `dependency-review` stays red until the owner enables the repository's Dependency graph setting (a repository setting). Signed commits are guidance, not enforced ([signed-commits.md](signed-commits.md)).
- **Proof.** The CI jobs `secret-scan`, `codeql`, `osv`, `images`, `workflows` (all required checks) and the lint guards; the Scorecard workflow has run.

## 14. The attack suite, fuzzing, ZAP, the coverage gate and mutation checks

- **Problem.** Tests written next to the code share its assumptions. What was never tested is the assembled system as an attacker meets it, and a test that cannot fail proves nothing (T-33).
- **Decision.** [tests/attack](../tests/attack) ([ADR-24](decisions.md), [attack-catalogue.md](attack-catalogue.md)): black-box attacks through the TLS proxy as the seed users, with a few test-only doors that exist only in the test compose file; fast-check fuzzing with a fixed, printed seed in CI and a random one nightly; an OWASP ZAP baseline with an allow-list that must carry a reason and an expiry ([check-zap-allow.mjs](../scripts/check-zap-allow.mjs)); a gate in `pnpm lint` ([check-threat-coverage.mjs](../scripts/check-threat-coverage.mjs)) that fails when a threat has neither an existing test nor an accepted risk with an owner, a rationale and an upgrade path, or when the catalogue and the tests disagree. Mutation checks are done **by hand** on purpose: apply one defect to the code, run the matching suite, and require a failure, then restore. Only that shows the test bites; a test that passes with the defence removed is decoration. [scripts/attack-mutation.mjs](../scripts/attack-mutation.mjs) automates the stage 9 mutants (rebuild, compare image ids so a stale container is not mistaken for a result).
- **Alternatives rejected.** A scanner only (finds classes, not the application's rules such as who may read which file); attack tests inside the existing suites; coverage percentages as evidence.
- **Trade-offs and limits.** The suite proves the absence of the attacks it contains and nothing more ([attack-catalogue.md](attack-catalogue.md), "Not attacked here"); it needs the full stack and takes minutes; the ZAP baseline is passive and finds classes only. Mutants are chosen by the author, so the check is as good as the author's imagination; the two surviving stage 9 mutants are documented redundant layers.
- **Proof.** CI `attack-tests` (required), `attack-nightly`, the manual `attack-mutation` workflow; the threat-coverage gate verified by deliberate breakages; real defects the attacks found and fixed (listed in [attack-catalogue.md](attack-catalogue.md)).

## 15. The frontend

- **Problem.** An interface is where XSS, clickjacking and token exposure happen, and where a security control can be broken to make a screen easier (T-04, T-07, T-12, T-31).
- **Decision.** Server-rendered React in the BFF, no client-side token storage, one script on the whole site (a countdown for the session expiry); a strict CSP with a per-request nonce and `strict-dynamic`, no `unsafe-inline` or `unsafe-eval`, `frame-ancestors 'none'`, a build-time Tailwind stylesheet and self-hosted fonts so `style-src` needs no exception; every state-changing form carries the synchronizer token; all output is escaped by React and there is no `dangerouslySetInnerHTML`; classification is shown in words as well as colour ([ui.md](ui.md), [ADR-25](decisions.md)).
- **Alternatives rejected.** A single-page app with a token in memory ([section 3](#3-the-bff-backend-for-frontend)); a UI kit or CDN fonts (remote assets and runtime style injection); relaxing the CSP for a nicer widget.
- **Trade-offs and limits.** Little client interactivity by design; the break-glass result page is reached by a redirect with the justification in a two-minute `HttpOnly` cookie because a route handler cannot render React in Next.js 16 ([ui.md](ui.md)); no assistive-technology, mobile or non-Chromium testing (**unverified**).
- **Proof.** [tests/e2e](../tests/e2e): real Chromium with real sign-ins; zero CSP violations on every page of every role, injected inline script, handler and foreign image refused and reported, no framing from another origin, cookie attributes, no token in script-reachable places, axe without serious findings in both themes, keyboard order, the theme toggle under the CSP; CI `e2e-browser`. [contrast.test.ts](../apps/web/src/ui/contrast.test.ts) checks every colour pair of both themes.

## 16. What was deliberately not built

| Not built | Why | Where it stands |
|-----------|-----|-----------------|
| A token revocation list or introspection | Offline validation is the resource-server model; the window is at most five minutes and is measured. Upgrade path for SECRET reads: introspect, or check `sid` against a back-channel logout list | AR-02, [threat-model.md](threat-model.md) stage 4 notes |
| TLS between internal components | The prod-like stack isolates them on internal networks; adding mutual TLS needs a certificate authority and rotation that this lab does not run | AR-01 |
| External anchoring of audit checkpoints | Needs a second system or a write-once store | AR-08 |
| A key management service | Key rings with ids and rotation procedures exist; a KMS or HSM is a deployment decision | [hardening.md](hardening.md) section 3, [asvs.md](asvs.md) (V6, V8) |
| Storage quota, re-scan of pending files, attachment deletion | Scope of the lab | AR-06, AR-11 |
| Account recovery, user notification, a breached-password check, MFA for the Keycloak admin console | Identity-provider features not enabled | AR-14 |
| Step-up freshness, a second approver for break-glass | Policy refinements beyond the stage plan | AR-03, AR-09 |
| Multi-replica operation and shared rate-limit counters | Not run, not measured | AR-04 |

Each row is an entry with an owner, a rationale and an upgrade path in [accepted-risks.md](accepted-risks.md), and the gate in `pnpm lint` fails if a threat points at an entry that is not complete.
